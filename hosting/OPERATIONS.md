# ohmy-seo.ru — эксплуатация

OAuth-брокер: пользователь входит Яндексом или Google, сразу выдавая рабочие
разрешения, а его аккаунты становятся доступны MCP-клиентам — облачным
(`mcp.ohmy-seo.ru`) или локальным (скрипт синхронизации).

## Состав

| Контейнер | Образ | Порт на хосте | Назначение |
|---|---|---|---|
| `ohmy-seo-web` | `ohmy-seo-web` | 127.0.0.1:3300 | Next.js: вход, кабинет, REST API |
| `ohmy-seo-gateway` | `ohmy-seo-gateway` | 127.0.0.1:3301 | Облачный MCP (Streamable HTTP) |
| `ohmy-seo-pg` | `postgres:18-alpine` | — | Пользователи, подключения, ключи, аудит |
| `ohmy-seo-redis` | `redis:8-alpine` | — | Кеш access-токенов |

Тома: `ohmy-seo_pg_data`, `ohmy-seo_redis_data`, `ohmy-seo_tenants`.

## Развёртывание и перенос на другой VPS

Стек самодостаточен: `ohmy-seo` клонируется и собирается внутри образа шлюза,
на хосте нужен только Docker.

```bash
rsync -az ./ user@newhost:/srv/ohmy-seo/      # без .env
scp .env user@newhost:/srv/ohmy-seo/.env      # или соберите заново
ssh user@newhost 'cd /srv/ohmy-seo && docker compose up -d'
```

Перенос данных — дамп Postgres и том `tenants` (последний воспроизводим, можно не переносить):

```bash
docker compose exec -T postgres pg_dump -U ohmy_seo ohmy_seo | gzip > ohmy-seo.sql.gz
```

`docker compose up -d` идемпотентен: имя проекта и `container_name` зафиксированы,
поэтому повторный запуск и перезагрузка хоста переиспользуют те же контейнеры и
не плодят копии. Проверено — после трёх подряд `up -d` контейнеров ровно четыре.

## Секреты

Всё в `.env` (0600, не в git):

- `OHMY_SEO_MASTER_KEY` — AES-256-GCM для всех чужих токенов. **Бэкапить отдельно
  от базы.** Потеря = все пользователи проходят авторизацию заново.
- `SESSION_SECRET` — подпись cookie сессии.
- `POSTGRES_PASSWORD`.
- `YANDEX_CLIENT_ID/SECRET`, `GOOGLE_CLIENT_ID/SECRET` — OAuth-приложения.

Ключ тенанта не хранится: он выводится как `sha256(master || "tenant:<id>")`,
поэтому базы тенантов невзаимозаменяемы и лишних секретов не появляется.

## Как устроен облачный MCP

1. Клиент присылает `Authorization: Bearer ohmy_...` на `POST /mcp`.
2. Шлюз находит пользователя по SHA-256 ключа.
3. Освежает токены, срок которых истекает в ближайшие 5 минут, и пишет их
   в Postgres — чтобы веб и шлюз не разъехались на ротации refresh-токена Яндекса.
4. Материализует `/data/tenants/<user>/state.db` — схему, которую читает `ohmy-seo`.
5. Поднимает дочерние stdio-серверы под провайдеров пользователя и отдаёт их
   инструменты одним списком.

Refresh-токены в тенантную базу **не** попадают: дочерний процесс получает
короткоживущий access-токен и заглушку, а фоновой таймер переписывает строку
раньше, чем она истечёт. Скомпрометированный дочерний процесс не может
выпустить новые токены.

Простаивающие тенанты выгружаются через `TENANT_IDLE_MS` (15 минут), поэтому
долгоживущий контейнер не копит процессы.

## OAuth-приложения Яндекса

Яндекс разрешает **не более трёх сервисов на одно приложение**, а login + Метрика +
Вебмастер уже исчерпывают лимит. Поэтому приложений два, оба на ki.vech@yandex.com:

| Приложение | ClientID | Доступы | Redirect URI |
|---|---|---|---|
| ohmy-seo | 78f07eefec8a4249addfd66e55600e2e | login:email, login:info, metrika:read, metrika:write, webmaster:hostinfo, webmaster:verify | /api/oauth/yandex/callback |
| ohmy-seo Директ | 43ecf3192a9547a085119513de3585e2 | direct:api, audience:read, audience:write, cloud:auth | /api/oauth/yandex-direct/callback |

В коде это провайдеры `yandex` и `yandex-direct`. В тенантной SQLite оба токена
одного логина лежат в таблице `accounts`, причём директовый — под меткой
`<логин> (Директ)`, иначе сработал бы UNIQUE(label).

Следствие для агента: инструменты Директа надо звать на аккаунте с суффиксом
`(Директ)`, остальные — на основном. Одним аккаунтом это не покрыть, пока Яндекс
держит лимит в три сервиса.

## OAuth-приложение Google

Проект Cloud Console **vechkasov-pro** (883647253159), аккаунт kirill.vech@gmail.com.
Клиент `ohmy-seo web`, redirect `/api/oauth/google/callback`.

Скоупы только на чтение: `webmasters.readonly`, `analytics.readonly`,
`tagmanager.readonly` плюс `openid/email/profile`. Права на запись не
запрашиваются, потому что запись на платформе выключена глобально; чтобы её
включить, нужны широкие скоупы (перечислены комментарием в `providers.ts`) и
повторное согласие всех пользователей — задним числом Google их не выдаёт.

`include_granted_scopes` **не ставить**: он выполняет инкрементальную
авторизацию и затягивает в наш экран согласия все скоупы, ранее выданные в
проекте, включая Gmail от установленного там же gmail-mcp.

`prompt=select_account`, не `consent`: иначе экран согласия показывается при
каждом входе. Если Google не вернул refresh-токен и в базе его нет, колбэк
один раз повторяет флоу с `prompt=consent` (защита от цикла — подписанный state `retried`).

## Одна кнопка на провайдера

Пользователь видит «Подключить аккаунт Яндекса» и «Подключить аккаунт Google».
Для Яндекса это цепочка из двух OAuth-приложений подряд (`chain=1` → подписанный OAuth state → колбэк перебрасывает на `yandex-direct`), в кабинете оба
подключения группируются в одну карточку по `PROVIDER_FAMILY`. «Отключить»
отзывает все подключения группы сразу.

Кнопка «Добавить аккаунт» сразу открывает OAuth провайдера без ввода почты.
Старые адреса `/app/connect/yandex` и `/app/connect/google` перенаправляют туда же.
Первый шаг не передаёт `login_hint`, чтобы не закреплять прежний аккаунт. Яндекс
получает `force_confirm=yes`, Google — `prompt=select_account`; при необходимости
получить refresh-токен Google используется `select_account consent` с проверкой
того же ID и единственной повторной попыткой.

Оба OAuth-токена Яндекса проверяются через `login.yandex.ru/info`: базовые
`id` и `login` доступны даже без login-скоупов. Второй шаг получает `login_hint`
выбранного аккаунта и должен вернуть тот же ID. Смена аккаунта на втором шаге
прерывает цепочку, не перезаписывая чужое подключение.

OAuth state подписан и привязан к провайдеру, сессии ЛК и конкретному шагу.
Пропажа/смена сессии не превращает подключение в новый вход. Повторная авторизация
обновляет строку `(provider, subject)`; перенос строки между разными кабинетами
запрещён. Каждая карточка отключает только свои подключения.

Облачный MCP проверяет состав подключений при запросе: при изменении набора
перезапускает процессы пользователя, удаляет отключённые токены из SQLite и
подключает новые серверы. API-ключ менять не нужно.

### Перенос старого подключения Директа

Перед выкладкой сохраните `pg_dump`. Скрипт
`deploy/migrate-direct-identities.mjs` запускается внутри контейнера gateway:
по умолчанию только проверяет настоящий ID каждого старого токена.
`APPLY_DIRECT_IDENTITY_MIGRATION=true` включает транзакционное обновление.
Идентификаторы строк и токены сохраняются; значения токенов скрипт не выводит.
При конфликте ID или конкурентном изменении вся транзакция откатывается.

### Проверки из локального репозитория

Исходники размещены в `hosting/` основного репозитория.

```bash
npm ci --prefix hosting
npm ci --prefix hosting/apps/web
npm ci --prefix hosting/apps/gateway
npm test --prefix hosting
npm run build --prefix hosting/apps/web
npm run typecheck --prefix hosting/apps/gateway
```

Интеграционный тест Postgres запускается только с `TEST_DATABASE_URL`,
указывающим на отдельную временную тестовую базу, никогда на рабочую.

## Совместимость MCP и шлюза

Релиз v0.9.0 включает исправления ключа шифрования отдельного пакета и секунд
в `google_accounts.expires_at`. Шлюз пишет время в секундах для всех провайдеров.
Нельзя запускать этот шлюз с MCP до v0.9.0: старый Google-брокер ожидает миллисекунды.
Пакеты получают собственную переменную мастер-ключа, рабочую папку пользователя
и общий путь его SQLite для кеша (`MCP_YANDEX_SEO_DB_PATH`).
